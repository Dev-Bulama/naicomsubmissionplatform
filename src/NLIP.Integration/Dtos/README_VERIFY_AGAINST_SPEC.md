# NAICOM DTO field verification required

This session's environment blocked outbound access to `portal.naicom.gov.ng` (not on the
container's network allowlist), so the DTOs in this folder were **not** generated by reading the
live `NAICOM_PORTAL_API_v0_v1.html` spec. They were designed from the field list given in the task
brief (SID/Secret auth, Create/Update/Renew/Terminate/Query/Delete, Individual Life & Group Life)
and standard patterns used by comparable Nigerian regulatory-portal rendition APIs.

**Before pointing this integration at a real NAICOM environment**, fetch the actual spec and
reconcile it against every file in `Dtos/Auth`, `Dtos/IndividualLife`, `Dtos/GroupLife`, and
`Dtos/Common`, then adjust:

- Exact field names/casing (NAICOM may use PascalCase, camelCase, or snake_case)
- Exact endpoint routes/verbs (`NaicomApiEndpoints.cs` centralizes every route — only one file to edit)
- Auth flow: token header name, token lifetime, whether SID/Secret are sent as a header, query
  string, or JSON body
- Required vs optional fields, enumerated value lists (e.g. gender codes, relationship codes),
  and any regulator-specific identifiers (RC number formats, state codes, etc.)
- Response envelope shape (this scaffold assumes `{ statusCode, message, data }`)

Everything downstream (the AutoMapper profiles in `Mapping/`, the resilience-wrapped HTTP client in
`Client/`) is written so that adjusting the DTOs and `NaicomApiEndpoints` is the only change needed —
no other layer touches raw NAICOM JSON.
